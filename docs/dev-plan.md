# 拼字蜂 Phase 1 開發與驗證計畫

設計計畫書（`game-design.md`）說的是「要做什麼」，這一份說的是「怎麼做、怎麼確定做對了」。
重點在中間三章：我在沒有你幫忙的情況下，用哪些方式自己測試、量測與除錯，以及哪些事我確實測不了。

---

## 1. 總體原則與節奏

| 原則 | 實際作法 |
|---|---|
| **一次只做一小步** | Phase 1 拆成六步，每步做完就 commit + push 並附上驗證數字，不堆一大堆才給你看 |
| **每一步都能單獨跑** | 不存在「做到一半整個壞掉」的狀態；任何時間點拉下來都是可以打開的 |
| **不碰現有的 app** | 遊戲蓋在新網址 `/game`，現在的練習頁完全不動。小孩隨時可以照常練，不會有空窗期 |
| **卡住就說卡住** | 某一步做不出來，我會說卡在哪裡、我試過什麼，而不是硬幹或靜靜跳過 |
| **驗證不過就不往下走** | 每步有寫死的驗收數字，沒達標就回頭修，不累積技術債 |

時間不是限制。限制是**我不能假裝測過**——這份計畫大部分的篇幅在講這件事。

> 這個專案之前有過一次教訓：第一版寫完就上線，結果白畫面，而我第一反應是叫你去查 console。
> 你那句「全新寫好就要查 console，很弱欸」是對的。從那之後我改成自己先重現、自己先量，這份計畫是把那個做法制度化。

## 2. Phase 1 拆成六個小步

Phase 1 的目標只有一個：**「聽到 → 打字 → 敵人被擊退 → 打完爆掉」這個迴圈好不好玩。**
沒有地圖、沒有能力、沒有商店、沒有 Meta。就一隻敵人、一個字接一個字。

| 步 | 內容 | 驗收標準（寫死的數字） |
|---|---|---|
| **1.1 骨架與除錯基建** | 全螢幕場景、固定時間步、可設種子的亂數、debug overlay、輸入錄製與重播、給 bot 用的除錯 API | bot 能跑完 20 個字不崩；同一個種子重播結果完全一致 |
| **1.2 輸入層** | window 層 keydown、忽略 `e.repeat`、輸入緩衝、焦點鎖定、Backspace、失焦暫停、輸入法偵測 | 500 次按鍵的延遲直方圖，p95 ≤ 16ms；按著不放不連發；快打時一個按鍵都不被吃 |
| **1.3 逐字母視覺回饋** | 能量槽、敵人裂痕、蜂針、受擊白閃、字母碎片粒子、物件池 | 戰鬥中 60fps，p95 影格 ≤ 16.7ms；連續 3 分鐘 heap 不持續上升 |
| **1.4 音階打擊音** | C-D-E 上行音階、錯誤音、擊殺音，全部 Web Audio 合成 | keydown → 發聲 p95 ≤ 20ms；靜音模式下每個聲音事件都有對應視覺事件 |
| **1.5 敵人逼近與擊退** | 時間公式、擊退、抵達扣血、hit stop、鏡頭震動 | 時間公式單元測試全過；bot 用三種打字速度各跑 200 場，失敗率落在預期區間 |
| **1.6 難度校準與收尾** | 用 3 個熟字量按鍵間隔 → 建議起始難度；整合成完整一輪 | bot 模擬慢／中／快三種手速，建議難度都正確 |

**順序是有理由的。** 1.1 先做除錯基建看起來像繞路，但它是後面五步的地基：
沒有可重播的確定性，就量不出延遲、跑不了 bot、也做不出視覺回歸。先花一步把工具做好，後面每一步都便宜。

做完 1.6 就**停下來**，讓你兒子在電腦上玩五分鐘。這是設計計畫書裡那個止損點，我不會自己跳過去。

## 3. 我怎麼自己測

我手上有 Node、無頭瀏覽器（Chromium）與 Playwright，靠這三樣可以做到下面七件事。
前面這幾天抓到的 bug（白畫面、元素延遲、自動登入、蜜蜂縮放）幾乎都是靠這套做法找出來的，現在把它擴充到遊戲。

### 1. 自動化玩家 bot（最重要的一個）

Playwright 可以發真正的鍵盤事件。我寫一個機器人來玩這個遊戲：從除錯 API 讀出目前該打的字，
依照設定的**每字母間隔與打錯機率**一個一個按下去，模擬小四生的手速。

意義很簡單：**我可以在沒有人的情況下把這個遊戲玩幾千次。**
崩潰、卡死、數值跑掉、輸入被吃——這些不用等你兒子碰到。

### 2. 純邏輯模擬器（不跑畫面）

戰鬥邏輯寫成不依賴 Phaser 的純函式，就能用 Node 直接跑。幾秒鐘一萬場，用來驗證平衡
（各關卡失敗率、每組平均通關場次、能力勝率排行）。這把「邏輯對不對」與「畫面對不對」徹底分開，兩邊都更好查。

### 3. 延遲量測（手感的核心，必須是數字）

「感覺很快」不算驗證。具體做法：在 keydown 當下記時間戳，在畫面狀態真的改變後的第一個影格再記一次，
兩者相減；聲音則比對 AudioContext 的排程時間。跑 500 次按鍵出直方圖，**我會把 p50 與 p95 寫在報告裡**。

### 4. 影格效能與記憶體

每個影格的耗時逐筆錄下來 → p50／p95／最差影格／掉格次數。同時追蹤 JS heap：
**持續上升就代表戰鬥中有在新建物件**，那會變成偶發的 GC 卡頓——這種 bug 玩的人只會說「有時候怪怪的」，
最難查，所以我直接監控它。另外用 CPU 降速模擬較慢的電腦，不能只在最好的情況下測。

### 5. 視覺回歸（截圖比對）

固定種子 + 固定時間步 → 同一個畫面每次跑都一模一樣 → 跟基準圖比對。
改 A 功能不小心弄歪 B 畫面這種事，機器比人眼可靠。

### 6. 靜音可玩性檢查

設計要求「所有聲音回饋都要有對應的視覺回饋」。這可以直接程式化驗證：用 bot 跑一場，
把所有聲音事件與視覺事件列出來對，**有聲音卻沒視覺的就是 bug**。

### 7. 跨裝置版面

桌機 1920×1080、1440×900、iPad 橫向（含螢幕鍵盤彈出後的高度）三種尺寸各截一輪，
量測有沒有超出、有沒有遮到輸入區。這一招之前抓「超頁了」那次就是靠它。

## 4. 我怎麼除錯

### 規矩：先重現，再修，再重新量一次

這不是口號。之前那個「登入頁快閃一秒就自己登入」的 bug，我是先寫了一個帶正確簽章 cookie 的測試，
把它穩定重現出來，才動手改。不能穩定重現的 bug，改完也不知道有沒有好。

### 遊戲特有的：輸入錄製與重播

遊戲的 bug 很多是「偶發的」，而偶發的 bug 用傳統方式根本抓不到。所以我會把**每一個輸入事件加上亂數種子全部錄下來**，
搭配固定時間步，一場戰鬥就能一模一樣重跑。

這件事順便解決了一個很實際的問題：**你兒子說不出來到底發生什麼事。** 他只會說「剛剛怪怪的」。
有了重播，他只要按一下「剛剛怪怪的」，我拿到檔就能完整重現他看到的畫面。

### Debug overlay（他會覺得很酷那個）

按 F3 叫出來：影格時間、物件池使用量、目前種子、敵人狀態、輸入緩衝區。
跟 Minecraft 的 F3 一樣——我拿來除錯，他拿來當彩蛋。

### 事件環狀緩衝區

最後 500 個事件常駐記憶體，出錯時連同當下狀態一起 dump。
不用事先猜要印什麼 log，出事時現場就在手上。

### 我不會做的事

叫你去開開發者工具、叫你貼 console 訊息、叫你「再試一次看看」。
你的工作只有一個：**跟我說哪裡不對勁，或者讓孩子玩完告訴我好不好玩。**

## 5. 每一步我會交給你什麼

不是「做好了」三個字。每一小步結束時，你會拿到一份固定格式的短報告：

| 欄位 | 內容 |
|---|---|
| 做了什麼 | 一到三行 |
| **量出來的數字** | 延遲 p50／p95、影格 p95、掉格次數、bot 跑了幾場、失敗率——跟驗收標準對照 |
| 畫面 | 截圖或短影片，讓你直接看到現在長什麼樣 |
| **沒達標的部分** | 有就寫，並說我打算怎麼辦 |
| **這一步我測不到的** | 每步都有，不省略 |
| 下一步 | 打算做什麼 |

兩個我會守的規矩：**數字沒達標就不說它過了**，以及**測不到的事我不會寫成測過了**。
這兩句看起來多餘，但它們是這份計畫能不能信的全部基礎。

---

## 6. 我無法驗證的事

上面那一大套能覆蓋很多，但不是全部。這些是我確實碰不到的，寫清楚比事後裝傻好：

| 測不到的 | 為什麼 | 怎麼補 |
|---|---|---|
| **好不好玩** | 這不是技術問題，機器量不出來 | 這就是 Phase 1 做完要讓他玩五分鐘的原因 |
| **中文輸入法行為** | 無頭瀏覽器沒有注音輸入法 | 我會把偵測邏輯寫好並自測到極限，但**真正的驗證要靠你兒子在注音模式下試一次** |
| **真實 TTS 發音** | 無頭瀏覽器沒裝任何語音 | 重聽、慢速、例句的時間點我只能測程式邏輯，聲音本身要你那邊聽 |
| **你電腦的實際效能** | 我的環境跟你家電腦不同 | 我用 CPU 降速模擬較差的機器，並把影格數據輸出到畫面上，你可以直接看 |
| **真實部署後的樣子** | 這個環境連不到 Render 跟 Atlas | 每次推上去後你點一下網址告訴我有沒有開，不用查任何東西 |
| **真實鍵盤的手感** | 程式發的鍵盤事件跟真人敲不完全一樣 | 延遲數字我能量，但「敲起來爽不爽」還是要人 |

最上面那一行才是重點。**我能保證它不崩、不卡、延遲夠低、數值合理，但我保證不了它好玩。**
所以那五分鐘不是儀式，是真的要拿來做決定——他眼睛沒亮就不往下做。

## 7. 這對程式架構的硬性要求

上面那些測試手段不是寫完程式再加的，它們反過來決定程式要怎麼寫。
這三件事必須在 1.1 就定下來，之後再補就要重寫：

**一、確定性**——固定時間步加上可設種子的亂數，絕不直接用 `Math.random()`，也不讓遊戲邏輯看真實時間。
沒有這個就沒有重播、沒有視覺回歸、模擬器也不可信。

**二、邏輯與渲染分離**——戰鬥規則（時間公式、擊退、扣血、Combo、能力效果）寫成完全不碰 Phaser 的純函式，
Phaser 只負責把狀態畫出來。這樣才能用 Node 跑一萬場平衡模擬，而且邏輯的 bug 不會跟畫面的 bug 糾在一起。

**三、除錯 API**——遊戲把內部狀態開一個唯讀的窗口出來（目前該打的字、敵人位置、血量、影格數據、事件日誌）。
bot 靠它玩、延遲量測靠它計時、靜音檢查靠它對帳。正式環境可以關掉，但預設開著也無害——F3 畫面就是它的前端。

> 順序上看起來是「先做工具再做遊戲」，有點反直覺。但這三件事如果等到 Phase 3 才想補，
> 得把戰鬥核心整個拆掉重寫。現在花一步，後面每一步都便宜。

---

## 8. Phase 2~6 概覽與各自的驗證重點

後面的階段先寫到這個粗度就好——Phase 1 的結果很可能會改變後面的做法，現在把它們規劃太細是浪費。

| Phase | 重點 | 驗證重點 |
|---|---|---|
| 2. 一場戰鬥 | 多敵人、血量、Combo、三段難度 | **平衡模擬器上線**：失敗率落入目標區間 |
| 3. Run 結構 | 地圖、三選一、王關、認證關 | 模擬器跑完整 Run：每組平均 5~6 場通關 |
| 4. Meta | 蜂蜜、角色、圖鑑 | 跨場進度存檔的正確性與離線同步 |
| 5. 內容量產 | 能力擴到約 45、敵人、biome、週修飾 | **每加一批能力重跑一次勝率排行**，揪出過強過弱 |
| 6. 打磨與收尾 | 效能、轉場、無障礙 | 全組測試重跑一遍 |

### 時程我不打算給日期

你說不要趕，我就不給一個做不到的日期。我給的是順序與驗收標準：一次一步，每步交一份帶數字的報告，達標才往下走。

唯一有外部相依的是單字庫：`word-bank.js` 要從 `part: 1~4` 改成通用的組，Week 1~18 才貼得進來。
這件事跟遊戲無關，可以隨時插進來做。
