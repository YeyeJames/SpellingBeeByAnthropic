# 實測前檢查　步驟二：共用裝置與資料隔離

> 這一步**沒有改任何程式**。以下的修正都只是提案，等家長逐筆確認。
> 重現腳本：`node scripts/audit/step2-repro.mjs`（真的伺服器＋假資料庫＋真的 Chrome）。
> 每個結果都跑了 3 次，3 次都一樣。

## 背景：為什麼會有這類問題

同一台筆電、同一個 Chrome 上，兩個孩子共用**同一個登入 cookie**，以及**同一份「現在是誰」的本機紀錄**。
在任何一個分頁換人，整個瀏覽器就換人了。
但已經開著的頁面，記憶體裡還是舊的那個人：它照舊以為自己是 Pierce，送出去的資料卻被伺服器記在「cookie 上現在是誰」的名下。

## 結果

| 編號 | 情境 | 結果 | 嚴重度 | 可能性 |
|---|---|---|---|---|
| S1 | 分頁一 Pierce 在練習；分頁二有人換成 Allen；回到分頁一繼續答 | **確認是問題**：之後的答案（Pierce 課本的字）全部記到 **Allen** 名下；分頁一的導覽列還寫著 Pierce | P1 | 中低（要開兩個分頁） |

| S3 | Pierce 離線作答（排進佇列）→ 換 Allen → Pierce 回來 | **沒有問題**：每一筆都記到 Pierce 自己名下 | — | — |
| S4 | 練習途中登入失效（登入滿 30 天、或別的分頁按了登出） | **確認是問題**：之後的答案**全部消失**，伺服器沒有，佇列也沒有；畫面照樣繼續，看不出任何異常。練完一組的紀錄也會一起消失，所以遊戲不會解鎖 | P1 | 低（剛好在練習中途失效才會發生） |

### Q2（Allen 帳號裡的 Pierce 課本舊紀錄）
逐一檢查了所有讀練習紀錄的地方。複習、戰役、弱點章、重學加倍、遊戲結算，全部都只看自己那一本，**不受影響**。
只剩兩個「總數」會把舊紀錄算進去：個人檔案的「總共練了幾題」，以及家長報告裡的練習正確率。這兩個是歷史紀錄，**建議不改**。
S1 很可能就是這些舊紀錄的來源之一。

### 登入多久會失效
登入後 **30 天**失效，而且不會因為一直在用而延長。孩子平常不會回選人畫面，所以大約是「上次選名字的那天＋30 天」。
失效當下如果不是在練習中途，只會被帶回選人畫面，點一下名字就好，不會掉資料。

## 現在就能做、零風險的因應（不用改程式）

1. **一次只開一個分頁**玩這個網站。
2. **換人一律用右上角名字旁邊的 ▾ →「換人玩」**，不要用「上一頁」回到別人的畫面。

這兩點就能避開 S1 和 S2。S4 的機率本來就低。

## 修正提案（等確認，尚未動手）

根本原因只有一個：**頁面以為的人**跟**伺服器以為的人**可能不一樣，而伺服器從來不檢查。
提案分成三筆，可以分開決定：

### 提案 2-A：伺服器檢查「你是誰」（修 S1、S2）
- 每個請求都帶上「這一頁以為自己是誰」。伺服器發現跟登入的人不一樣，就拒絕，回一個專用的錯誤。
- 被拒絕的資料**不丟掉**：留在原本那個孩子的佇列裡，等他下次選回自己時再送。
- 頁面顯示「現在這台電腦是 Allen，這一頁是 Pierce 的」，並帶回選人畫面。
- 回到一個「從記憶體還原」的頁面時，順便比對一次是誰，不一樣就重新載入。
- 沒有帶這個資訊的請求（部署當下還開著的舊頁面）照舊放行，不會突然全部被擋。
- **動到的地方**：背景同步佇列（最核心的一塊）、api.js、伺服器的登入檢查、遊戲結算、行為紀錄。
- **風險**：中。動到的是每一筆資料都會經過的路。

### 提案 2-B：登入失效時資料不丟（修 S4）
- 背景佇列遇到「沒有登入」時，改成**保留資料、停止送出、帶回選人畫面**。孩子選回自己的名字之後，照原樣補送。
- 靠 opId 去重，不會重複計分。
- **動到的地方**：背景同步佇列、行為紀錄上傳。
- **風險**：低到中。

### 提案 2-C：登入不再每 30 天失效（降低 S4 的機率）
- 伺服器設定改一行：有在用就自動延長，30 天完全沒用才失效。
- **動到的地方**：伺服器 session 設定一行。
- **風險**：低。唯一的副作用是每個回應多帶一個 cookie 標頭。

### 修正時的驗證計畫（三筆共用）
1. 先把 S1、S2、S4 寫成會失敗的正式測試。S2 用程式直接觸發「從記憶體還原」的那段處理，因為測試瀏覽器沒有這個功能。
2. 修正後：新測試連跑 3 次、全部 40 多支測試全綠。
3. **額外檢查不會誤擋**：正常的單一分頁使用（練習、遊戲、戰役、商店、小遊戲、換人），不能出現任何一次「你不是你」。
4. 部署當下還開著的舊頁面（沒帶新資訊）要照常能用。
5. 下一次對話時，重新看一次整個改動。
6. 推上去之後，請家長實際確認一次：開兩個分頁、換人、回到舊分頁作答，應該看到提示，而不是默默記錯人。

## 其他檢查過、沒有問題的

- 每個孩子自己的本機資料（佇列、進度、單字快取、偏好、行為紀錄）都分開存。全裝置共用的只有「現在是誰」、商店目錄、導覽列樣板、語音選擇，這幾樣本來就該共用。
- 刪除帳號：伺服器端的資料會全部刪掉。本機上那個帳號的資料會留著，但不會再被讀到，也不會被送出去，佔的空間很小。**建議不改**。

## 建議

1. **先採用上面兩點零風險的因應**，不改程式也能避開 S1、S2。
2. 三個提案的建議順序：**2-C（最小、最安全）→ 2-B → 2-A（最大、最後做）**。
3. 2-A 動到最核心的同步路徑。建議等真的 MongoDB 能用之後再做，測完才推。
